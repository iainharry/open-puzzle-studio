# Architecture

A running record of the decisions and what they cost. Written as they are made, with the
reasoning, so that a decision can be revisited on its merits rather than re-derived.

## 1. Three layers, fixed before the first puzzle (M1)

Borrowed openly from Simon Tatham's Portable Puzzle Collection: one front end, one shared
**mid-end**, one **back end** per puzzle.

The mid-end is the product. Undo, serialisation, seeded game identifiers and the session
are written once; a new puzzle is a table of callbacks. Twenty-two years of that collection
is the evidence that this is the right split for a collection app.

**It had to be decided on day one.** Open Jigsaw Studio's `app.ts` reached 4,650 lines —
a third of that codebase in one file — because it grew a milestone at a time with no seam
to grow along. Survivable for one puzzle type and fatal for six. Retrofitting the seam is
the most expensive thing this project could ever do, so it exists before there is anything
to put in it.

**`src/core/` and `src/puzzles/` run in Node with no DOM.** Same rule as the jigsaw
engine, same reason: it is what makes the thing testable. If a test of either needs jsdom,
the boundary has leaked and that is the finding.

## 2. `layout()` returns a scene rather than drawing one

The most repeated bug in the jigsaw project was that **asserting a thing is drawn is not
asserting what it shows**. A printable sheet that printed the answer passed four
assertions. A board that painted its bounding box instead of its outline passed all of
them. In both cases the test proved a drawing had happened.

So a puzzle describes itself as a `Scene` — a value, in cells rather than pixels — and the
shell turns that into pixels. A Node test can then read exactly what a player would see.
It also means screen, paper and any future renderer work from one description instead of
three that drift.

The cost: a puzzle cannot draw anything the scene language cannot express. That is the
point. When a puzzle needs something new, the language grows deliberately rather than one
puzzle quietly acquiring its own renderer.

## 3. `solve()` is the keystone

One function on the interface, carrying three features that would otherwise be three:

1. **Generation.** Nonograms cannot be generated by drawing a random bitmap — of random
   30×30 grids, 97.5% have more than one solution and only 0.4% are line-solvable
   (Wolter's survey, https://webpbn.com/survey/). Generation must be solve-driven.
2. **Honest difficulty.** Rate by which deductions were needed, never by clue count. The
   test is **two-sided**: Hard means the hard solver succeeds *and* the medium solver
   fails. Without the second half you ship easy puzzles labelled hard.
3. **Honest hints.** `steps[0]` from the player's own position is "here is the next
   deduction available, and this is why it works" — teaching the technique rather than
   giving the answer. Human-authored puzzle collections structurally cannot do this, and
   for a classroom it is the most valuable thing in the app.

**M1's solver throws rather than returning a stub.** A stub returning `{solved: false,
steps: []}` is indistinguishable from a real solver that found nothing, and M2's rating and
hints would be built on top of it without anyone noticing.

## 4. Snapshots for undo, and the watchdog (M1)

Carried from the jigsaw app's M22 and generalised. A command log needs an inverse written
per move type, and a collection app grows new move types every time a puzzle is added. A
snapshot is correct by construction and stays correct when somebody adds a puzzle in 2027
without reading this file.

Snapshots are the module's **serialised** state — a string — which keeps the mid-end
genuinely puzzle-agnostic and makes the fingerprint trivial. Revisit this if a puzzle ever
appears whose state is megabytes.

**The watchdog is the part worth keeping.** An undo feature does not rot on the day it
ships; it rots when a feature is added later and nobody records a step. So the session
fingerprints the state as of the last recorded step and counts mismatches, and the smoke
test presses every control and fails if the counter moves. A list of call sites somebody
remembered to wrap is not a test.

## 5. What the first smoke run caught

Worth recording because it is the argument for the smoke test existing at all. Every unit
test passed and the app looked right in a screenshot, and the smoke output read:

```
PASS  undo takes a mark back — "#####" -> "####."
```

A five-cell drag was five undo steps. Undoing a twenty-cell stroke would have taken twenty
presses. Nothing was broken, every assertion was green, and the feature was wrong — caught
only because the check printed *what* undo restored rather than merely that it restored
something. The fix was `beginChange`/`endChange` bracketing a whole pointer stroke, and the
assertion is now explicit.

## 6. Generation, measured (M2)

The solver came first, and everything else fell out of it. The numbers, on a desktop,
five puzzles per cell:

| Board | Gentle | Steady | Tricky |
| --- | --- | --- | --- |
| 5x5 | <1ms | 12ms | 24ms |
| 10x10 | <1ms | 1ms | 13ms |
| 15x15 | 9ms | 1ms | 58ms |
| 20x20 | 85ms | 3ms | **307ms avg, 775ms worst** |

Three things in that table are worth saying out loud.

**Generation blocks the main thread.** 775ms on a desktop is comfortably long enough on a
tablet to look like the app has died. M2 says "Making a picture…" and yields a frame so
the message paints — a courtesy, not a fix. The fix is a worker, and it is in the
limitations list rather than pretended away.

**A 20x20 Gentle is nearly impossible, and that is a fact about nonograms.** Trivial
line rules alone cannot usually finish a board that size, so the search spends its whole
budget (386 attempts) and falls back. The app then reports the difficulty it *achieved*
rather than the one requested, because a puzzle labelled Gentle that needs real work is a
lie told to a child.

**Steady is cheaper than Gentle on large boards.** Counter-intuitive and correct: the
complete line solver finishes almost any blob picture, so the search accepts on the first
or second try, while the gentle search rejects hundreds. The cost of generation tracks how
*rare* the requested difficulty is, not how hard the puzzle is.

## 7. Two bugs the solver tests caught, and why they were the dangerous kind

Both produced **confidently wrong answers** rather than missing ones, which is worse: a
solver that finds nothing is obvious, and a solver that deduces a square that is not
filled will cheerfully certify an unsolvable puzzle as solvable.

**`packRight` returned run positions in reverse order.** The overlap rule then compared
run 0's leftmost placement against run k-1's rightmost, and "deduced" filled squares in a
line where nothing was certain. The heart failed to solve, which is how it surfaced — but
the first symptom was a *contradiction*, two steps downstream of the actual error.

**`trivialLine` painted over squares already known the other way.** A 2x2 whose columns
say "empty" and whose rows say "filled" is a contradiction; the rows ran first and the
columns silently overwrote them, producing a "solved" grid from impossible clues. Now any
write that disagrees with a known square returns `'impossible'`.

Also worth recording: **three of the solver tests were wrong, not the solver.** Each
asserted a deduction that no arrangement actually supports. They were only caught by
working the line out by hand after the code disagreed — which is the right order, and the
temptation was to "fix" the solver to match the test.

## 8. Hints, in three strengths (M3)

The feature the whole project was argued for, and it cost almost nothing once `solve()`
existed — which was the point of building the solver first.

**Three strengths, not one button that fills a square in.** Press once and the line is
highlighted and nothing more. Press again and it says why. Press a third time and it does
it. Each press is a decision to be told more, and a child who only ever needs the first
one never sees the answer. A single button that completes a square takes the puzzle away
from the person solving it.

**A wrong board is checked first, and that order is the design.** Offering a deduction to
somebody whose marks already contradict the clues is deducing from a false premise and
sending them further wrong. It is also the mistake a child cannot find by staring, because
it is usually nowhere near where they are looking.

**It names the line, never the square.** Pointing at the square is surrender dressed up as
help. Naming the line hands back a problem small enough to re-check and leaves the finding
to them. The check is answer-free by construction: it never looks at the solution, only at
whether what the player wrote down can satisfy the clues — so it cannot leak, and a test
pins that by running it against a puzzle whose stored solution has been replaced with
rubbish.

**The easiest deduction, not the first one found.** `nextStep()` sweeps the tiers upward
and stops. A hint that reaches for a contradiction proof while an obvious overlap sits two
rows down teaches the wrong lesson about how these are solved.

**`nextStep()` is separate from `solve()` for cost.** A hint needs one deduction;
`solve()` works the whole puzzle out. On a 20x20 that is the difference between a button
press and a pause, on every press.

**The highlight is composed by the shell, not by `layout()`.** A `Scene` is a plain value,
so the shell spreads a new `highlight` onto the one the module returned. The puzzle module
does not know hints exist. That is the seam doing its job, and it saved an interface
change.

### What looking at the picture caught

Every assertion passed and the highlight was invisible. It was drawn as a 25%-alpha wash
*under* the marks — which reads beautifully on an empty square and not at all on a filled
one. The most important highlight in the app is "something in this row cannot be right",
about a row the player has **already filled in**.

Fixed by stroking the highlighted cells over the top as well. The new assertion samples the
canvas and requires the pixel to be the accent colour, because "a highlight was requested"
and "a highlight can be seen" are different claims — the same lesson as §2, arriving again
in a different costume.

## 9. A demonstration, not a video (M4)

Asked for as "a video or demonstration clip", and deliberately not built as one.

A video would be the largest asset in the build by an order of magnitude and would have to
be downloaded before the app worked offline. It could not follow the theme or the board
size, could not be paused on the step somebody did not understand, and would go stale the
first time a button moved — **the same failure as a hand-written guide**, which is exactly
why the sister project generates its guide from the live app rather than shipping one.

So the app plays itself, with the real solver on the real board. A few kilobytes of code
and no asset at all; it cannot go out of date because there is nothing to keep in step; and
it is steppable, which a video is not.

**It is only cheap because M2 and M3 exist.** A solver that already emits ordered
deductions, each with a sentence written for a ten-year-old and the moves to carry it out,
*is* a demonstration script. `buildScript()` is thirty lines.

Three things a clip of a person would have shown, and what was done about each:

- **A hand.** The demo draws a pointer ring onto the square it is about to mark. Drawn
  after the scene rather than put into `Scene`, because it belongs to the demonstration
  and no puzzle module should have to know that demonstrations exist.
- **Hesitation.** Each caption sits for almost two seconds before anything is marked. A
  demonstration that happens instantly teaches nothing.
- **A real person's mistakes.** Not shown, and that is the honest gap. What is shown is
  correct play only.

Other decisions: it runs at tier 1 only, because a demonstration that reaches for a
contradiction proof teaches a beginner the wrong thing about how these are solved; it is
capped at ten beats, because somebody who has watched ten deductions has the idea and the
eleventh is where they should be taking over; it always uses the same hand-drawn heart, so
a teacher can talk about it; the board is deaf to the pointer while it runs; and stopping
puts the player's own puzzle back.

### The race the "nothing threw" check caught

`demoWait()` read `this.demo.paused` **after** an await, having checked for null
**before** it. Pressing Stop nulls it from another turn of the event loop, so the check
said nothing about the world the read happened in. It threw a TypeError with no visible
symptom — the demo had already stopped and everything looked right.

That is the entire argument for the smoke test's last line. Thirty-nine checks of what a
player can see all passed, and the fortieth, which only asks whether anything threw, is
the one that found it.

## 10. Printing: blank by construction (M4)

A nonogram on paper is how most children will meet one in a classroom, so the sheet is the
whole artefact rather than a convenience.

The sister project shipped a printable sheet that **printed the answer** and passed four
assertions, because each checked that something had been drawn rather than what it showed.
The equivalent mistake here is passing the player's state into `printable()` instead of a
blank board — so `printable(puzzle)` takes no state at all. The signature makes the bug
unavailable rather than merely untaken.

SVG rather than a canvas screenshot: a printed clue is read at arm's length and a bitmap
scaled to A4 is soft exactly where the numbers are. It is also a few kilobytes of text
instead of a megabyte of pixels. The test counts what is in the sheet — twelve lines, every
clue, and **zero filled shapes**.

## 11. The second puzzle, and what it found (M5)

The plan's M5 was pictures — nonograms generated from a photograph. It was not built, and
the reason is in the plan's own risk register: *"the cheap insurance is M6 arriving early
enough that the mistake is found while there are two puzzles rather than six."* Pictures
are a feature on the puzzle that already exists and test nothing architectural; they are
also the most expensive milestone, because a solve-and-perturb loop multiplies a generation
cost that already blocks the main thread. So M5 is the second puzzle type, **Number
Place** — a Latin square with boxes — and the finding is the point of it.

### The shell was not puzzle-agnostic, and nothing could tell

`src/shell/app.ts` carried this comment from M1 to M4:

> It knows about `PuzzleModule`, `Session` and `Scene`, and nothing about nonograms. If a
> line in this file ever mentions a clue, a run or a picture, the seam this milestone
> exists to prove has leaked and that is the bug.

By M4 the file imported the nonogram module directly and mentioned pictures, clues and runs
in fourteen places: a hard-coded size list `[5, 7, 8, 10, 12, 15, 20]` offered to every
puzzle; a "Starter" dropdown built from the nonogram's hand-drawn pictures; `codeFor` and
`specFromCode`, which knew the shape of a nonogram spec; `chosenSpec(): PictureSpec`; a
help panel written in HTML about runs and crossing out; "% of the picture filled in"; the
demonstration's puzzle named inline as `{ kind: 'drawn', picture: 'heart' }`; the space key
swapping between the literal strings `'fill'` and `'cross'`; and `puzzle as { rows, cols,
tierUsed, title }` four times over, because the interface had no way to ask.

None of it was visible, because the only puzzle that existed was a nonogram. **A layering
rule with one implementation is a layering rule that has not been tested.**

### What `PuzzleModule` was missing

Seven things, each one a need rather than a convenience — the bar being "the shell cannot
render a second puzzle without it". The full list with reasons is at the top of
`src/core/types.ts`; in brief:

| Was | Is | Because |
| --- | --- | --- |
| `readonly tools` | `tools(puzzle)` | Its tools are its digits: four on a 4×4, nine on a 9×9 |
| *(nothing)* | `options()` + `specFrom()` | The puzzle says what it offers; the shell renders it |
| *(nothing)* | `encode()` / `decode()` / `normalise()` | Codes were built by the shell from a nonogram spec |
| *(nothing)* | `title()` / `describe()` / `instructions` | All of these were casts and hard-coded HTML |
| `SolveStep.line` | `look` + `where` | Its deductions are about **boxes**, which are neither rows nor columns |
| `Scene.band: number` | `{ col, row }` | A 6×6's boxes are 2 tall and 3 wide |
| `Mark` | gains `'shaded'` | Half its squares are fixed by the puzzle; nothing in a nonogram is |

The interface went from 15 members to 24. The shell is about the same length as before,
which is the honest outcome: the work did not vanish, it moved to where it belongs.
Replacing `SolveStep.line` with `look` *deleted* code — the shell and the demonstration
were each reconstructing a line's cells from an axis and an index, which is grid knowledge
neither had any business holding.

### The solver, again from the other end

Three tiers, each a kind of looking rather than a list of patterns, and each explainable to
a child in one sentence:

1. **Gentle** — one empty square left in a line, or one number left for a square.
2. **Steady** — this number can only go in one square of this box.
3. **Tricky** — suppose a number goes here, follow it, find that something breaks.

No naked pairs, no pointing pairs, no X-wings. They are *elimination* techniques: they rule
a number out without putting one in, and a player with no way to write "not a 7 here"
cannot use such a hint at all. Probing at tier 3 covers most of their effect and only
reports a result it can act on. The cost is stated rather than hidden: tier 3 here is
weaker than a full-strength Sudoku solver, so the difficulty labels are conservative.

Uniqueness comes free, by the same argument as the nonogram: every deduction is forced, so
a board the solver finishes by reasoning alone has exactly one answer. The generator never
checks it — and `countSolutions()` exists only so the **tests** can verify that claim by
exhaustive search rather than believing it.

### Measured, not assumed

Generation on a desktop, five runs each, and how often the requested tier was reached:

```
4x4 Gentle     0ms  5/5      6x6 Gentle    1ms  5/5      9x9 Gentle    9ms  5/5
4x4 Steady     3ms  0/5      6x6 Steady    3ms  5/5      9x9 Steady   12ms  5/5
4x4 Tricky     5ms  0/5      6x6 Tricky   35ms  2/5      9x9 Tricky  356ms  5/5
```

A 4×4 is always Gentle, whatever is asked for: there is not enough room for a contradiction
proof to be *necessary*. The app reports the difficulty it reached, never the one requested
— the same honesty the nonogram generator already owed.

### What looking at the picture caught, again

Three things no assertion was going to find, all from screenshots:

- The finish banner read "4×4 Gentle, **Gentle**, with no hints." The title already carries
  the rating.
- The How to play panel listed nine tools with nine near-identical explanations, filling
  the panel and pushing the demonstration button below the fold. Tools that share an
  explanation now share a line.
- Two smoke checks were weaker than they looked: navigating to a URL that differs only in
  its fragment does not reload the page, so "a code opens the puzzle it names" was reading
  back a field nobody had changed. Both now reload explicitly.

And one real bug the second puzzle's smoke run found in shared code: **Undo did not clear
an open hint**, so pressing Hint twice, Undo, then Hint once gave away the answer to
somebody who had asked for a nudge.

## 12. Decisions deliberately deferred

- **Cell size has no upper bound.** A 5×5 fills a desktop screen at 109px per cell, which
  looks odd to an adult and may be exactly right for a five-year-old on a tablet. Capping
  it would be inventing a number at a desk, which this project has a record of regretting.
  It is a playtest question.
- **22px minimum cell** is likewise a guess and is labelled as one in `render/scene.ts`.
- **Pencil marks**, and with them the second sticky input mode a number puzzle wants.
  Adults solving a 9×9 want to note "this could be a 3 or a 7". The shell has exactly one
  tool in hand at a time, and inventing a second dimension now would mean designing it
  against one puzzle — which is the mistake this milestone exists to undo. The children
  this app is for play 4×4 and 6×6, where notes are not needed. It is the first thing to
  look at if a third puzzle wants the same thing, because then it is a mid-end feature
  rather than a guess.
- **Assistance levels.** The hints already are the assistance, in three strengths. A
  separate "show me my mistakes" switch would make a different, easier puzzle and is worth
  having only if a teacher asks for it.
- **A generated guide.** The jigsaw app generates one from its live toolbar because it has
  sixty controls. This has about twelve, and How to play is now written by whichever puzzle
  is open. A teacher's guide is worth writing after watching a lesson, not before.

## 13. Known limitations

- **Generation blocks the UI.** Up to ~775ms for a tricky 20×20 nonogram and ~356ms for a
  tricky 9×9 number board, measured on a desktop; more on a tablet. Wants a worker — and
  now that both puzzles have the problem, the worker is a mid-end job rather than a
  per-puzzle one, which is worth knowing before it is built.
- **Difficulty cannot always be delivered.** A 20×20 nonogram cannot be Gentle; a 4×4
  number board cannot be anything but. The app falls back and reports what it got, but it
  does not explain in advance which combinations are impossible.
- **The per-puzzle dropdowns do not follow the open puzzle.** Opening a saved board sets
  the puzzle-type picker but leaves Size and Difficulty where they were, because a spec
  cannot be read back into a set of choices. The Code field and the status line both show
  the truth.
- **No pencil marks**, so a 9×9 at Tricky is a paper puzzle. Print exists.
- **Broken-board detection is honest, not complete.** It reports a repeat in a line or a
  line with nowhere left for a number. A single wrong entry that breaks nothing *yet* is
  not caught, in either puzzle, because the check never consults the answer — a hint here
  is reasoning the player could have done, not a look at the back of the book.
- **Hint counting is per puzzle, not per session.** Reopening a puzzle keeps the count,
  which is right, but there is no way to see it other than on finishing.
- **Nothing has been watched being played.** Two apps, twenty-nine milestones, no
  playtest. Every claim about what a child finds easy is a belief.

## Dependencies

None at runtime. Build only: TypeScript, Vite, Vitest, and Playwright for the smoke test.
